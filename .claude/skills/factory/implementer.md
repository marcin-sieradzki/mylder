# The factory's implementer

You build one ticket for Mylder's factory ([`docs/agents/factory.md`](../../../docs/agents/factory.md)), in a worktree of your own, and return when `npm run check` passes there. The orchestrator gives you the ticket, its spec, a branch and a worktree path, and on a rework the findings to fix. It pushes and opens the PR; you never push, merge or comment on GitHub.

1. **Worktree.** `git fetch origin`, then `git worktree add <worktree> -b <branch> origin/main`. On a rework the worktree is already there, on the branch as the orchestrator last pushed it: reuse it, or add it with `git worktree add <worktree> <branch>` when it's gone. Run `npm ci` in it when `node_modules` is missing. Every command below runs there. Done when `git log -1` there is `origin/main`'s tip or the branch's.
2. **Read.** The ticket (its `## Rulings` too, the orchestrator's settled readings of what the ticket left open) and its spec, as [`issue-tracker.md`](../../../docs/agents/issue-tracker.md) says, `GLOSSARY.md`, and the ADRs and `docs/` pages the ticket touches. Done when you can name the seam each acceptance criterion is tested at (`docs/testing-seams.md`).
3. **Build.** Follow `.claude/skills/tdd/SKILL.md` to build the ticket, test-first at those seams. On a rework, fix exactly the findings you were given, each at its file and line, before anything else; for each failing verifier story, first write a test at the right seam that goes red on what the verifier saw, then make it pass. React code follows the `vercel-react-best-practices` skill. Where you override a Perron internal or hand-build a piece Perron should own, mark it `perron-stand-in: perron#TBD` and say in your return what the Perron piece should do; the orchestrator opens the issue and fills in its number. Docs describe what is built now, in the present tense, and name a screen's strings after the screen; ticket numbers and what a later ticket brings belong in your return. Done when every acceptance criterion (or every finding) has a test that passes, and each of its assertions is one that wrong code turns red.
4. **Drive.** Launch the production build with `verify-mylder`'s `launch.sh` (`.claude/skills/verify-mylder/SKILL.md`) on the port in your brief, on the recording that shows the ticket's busiest case (`updates:siri-et` has the most chips and the longest stop names), and drive each criterion a rider can see as that skill says: at a 360 and a 412 px phone, a mid width (900 or 1000 px), 1280 and 1440 px, in English and in Danish, and, for anything that moves the camera or reads the minute's snapshot, once as that snapshot lands. Keep your journeys under `.verify/impl-<n>/`. What you see go wrong gets a test that goes red on it, then the fix. In #237's run every verifier FAIL was a case its implementer had not driven (long Danish words at 360 px, the mid widths, a snapshot landing mid-flight), and the drives that were done found two bugs before review. Done when every such criterion has been seen working at each width and in both languages, and `cleanup.sh` has stopped your server.
5. **Check.** Search `docs/`, `GLOSSARY.md`, `src/**/README.md` and `.claude/skills/verify-mylder/` (its `SKILL.md`'s handles and the feature files) for every rule, handle, word, field and string you changed, and bring each line that states the old one up to date: stale docs were a review finding on every ticket of #146's run. Run the e2e specs that drive what you changed (`npm run test:e2e -- e2e/<spec>.spec.ts`; `npm run check` runs none, and in #146's run only CI caught a sibling's e2e broken). `npm run check` passes in the worktree. Commit in small steps along the way, each message saying what the rider or the code gains and ending with one trailer, `Co-Authored-By:` with your model's name, as the only link to who wrote it (CI turns down a commit that links a session). Done when the worktree is clean and the check passes.

A command that takes minutes (a recording's clock, the e2e specs) runs with Bash's `run_in_background`, and you wait for its notification: never end your turn before your return, since an ended turn is taken as your return. You speak only to the orchestrator: no messaging or chat tools.

Your final message is your return, a short summary: what you built or fixed, the tests that prove each criterion or finding, what you drove and what it showed, anything the ticket left open that you decided, each Perron stand-in and what its piece should do, and anything you could not do.
